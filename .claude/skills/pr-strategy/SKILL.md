# PR Strategy

## Purpose

人間がPRを1本ずつ、要件と照らして無理なくレビューできる粒度を保つ。

## Source of Truth

PR粒度のルールは `docs/development/pull-request.md` の「PR Granularity」を正とする。

本Skillは、そのルールに沿ってPR計画を立てる手順を定める。ルールが食い違う場合は、`docs/development/pull-request.md` を優先する。

## Workflow

1. `docs/development/pull-request.md` の「PR Granularity」を確認する
2. 変更を、利用者から見て完結した機能の単位に分け、PR計画を作成する
3. 各PRについて、依存関係に従ってマージ順を決める
4. PRごとに、`commit-strategy` に従ってコミット計画を作成する
5. PRを作成する前に、変更行数を計測する
6. 目安(400行程度)を超えた場合は、分割を検討する。分割しない場合は、PR本文の「備考」に理由を書く

実装中に計画と異なる変更が必要になった場合は、PR計画を更新してから続ける。

## PR計画の形式

```markdown
| # | PR タイトル | 含む機能 | 見込み行数 | 依存先 |
| - | ----------- | -------- | ---------- | ------ |
| 1 | feat: ...   | ...      | 約 300     | -      |
| 2 | feat: ...   | ...      | 約 350     | #1     |
```

見込み行数には、生成ファイルと lock ファイルを含めない。

## Checklist

PR計画の各PRについて、以下を確認する。

- PR単体でマージしても、ビルドとテストが通るか
- PR単体で、要件と照らして動作を確認できるか
- 単独では使われない変更(共通部品、依存ライブラリの追加)だけのPRになっていないか
- 機能と無関係な変更(リファクタリング、依存ライブラリの更新、設定変更など)が混ざっていないか
- PRタイトルが「〜と〜」のように複数の目的を並べていないか
