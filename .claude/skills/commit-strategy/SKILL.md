# Commit Strategy

## Purpose

AIが大量のコードを生成した場合でも、
人間が変更内容を追跡・レビューしやすいコミット粒度を維持する。

## Principle

**1 Commit = 1 Logical Change**

1つのコミットには、原則として1つの論理的な変更だけを含める。

## Workflow

1. 実装を始める前に、コミット計画を作成する
2. 計画した単位ごとに実装し、その都度コミットする
3. 各コミットの前に、ビルドとテストを実行する
4. 実装中に計画と異なる変更が必要になった場合は、計画を更新してから続ける

実装をすべて終えてから、まとめて1つのコミットにしない。

## Rules

### 1. 変更の目的ごとにコミットを分ける

以下のように、変更の目的が異なる場合はコミットを分割する。

- 機能追加
- バグ修正
- リファクタリング
- 既存コードへのテスト追加
- ドキュメント変更
- 生成ファイルの更新
- 設定変更

新しく実装したコードに対するテストは、「テスト追加」として分けず、実装と同じコミットに含める（Rule 3）。

### 2. 関係のない変更を同じコミットに含めない

ある機能を実装するために必要な変更は、同じコミットに含めてよい。

一方で、その機能と無関係なリファクタリングやフォーマット変更は、別のコミットにする。

### 3. コミットを過度に細分化しない

コミット数を増やすこと自体を目的にしない。

以下のような関連する変更は、同一コミットにまとめる。

- 1つの機能を成立させるために必要な複数ファイルの変更
- 新しい実装と、それに直接対応するテスト
- 型定義と、それに伴う必須の実装変更

単独では意味を持たない変更（例：使われていない型だけを追加する）は、それを使う変更と同じコミットにする。

### 4. 各コミットでビルドとテストが通る状態を保つ

どのコミットをチェックアウトしても、ビルドとテストが通る状態にする。

分割によって途中のコミットでビルドが壊れる場合は、分割の単位か順序を見直す。

### 5. コミットメッセージで変更意図を説明する

以下の形式で記述する。

```text
<type>: <変更内容の要約>

<必要に応じて、変更の理由や補足>

Refs: #<Issue番号>
```

`<type>` は以下から選ぶ。

| type     | 用途                           |
| -------- | ------------------------------ |
| feat     | 機能追加                       |
| fix      | バグ修正                       |
| refactor | 振る舞いを変えないコードの整理 |
| test     | 既存コードへのテスト追加・修正 |
| docs     | ドキュメント変更               |
| chore    | 生成ファイルの更新、設定変更など |

対応するIssueがある場合は、必ず `Refs:` で参照する。

要約で「〜と〜」「〜および〜」のように複数の目的を並べる必要がある場合は、コミットを分割する。

`docs/development/` にコミット規約が定義されている場合は、そちらを優先する。

### 6. 大規模な変更はコミット計画を作成してから実装する

変更範囲が大きい場合は、実装前に論理的な変更単位と順序を整理する。

順序は、各コミットでビルドが通るように依存関係に従って決める。

例：

```text
1. feat: API仕様（OpenAPI）を追加
2. chore: OpenAPIから生成コードを更新
3. feat: Domain層を実装（テストを含む）
4. feat: Repository層を実装（テストを含む）
5. feat: Service層を実装（テストを含む）
6. feat: 認証を実装（テストを含む）
7. feat: Handlerを実装（テストを含む）
```

生成ファイルの更新コミットには、手作業による変更を含めない。

### 7. レビュー容易性を優先する

コミットを分割する際は、単純なコード量ではなく、以下を基準とする。

- 変更意図が明確か
- 差分を追跡しやすいか
- レビュー単位として理解しやすいか
- 他の変更と独立して確認できるか
