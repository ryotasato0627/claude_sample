# Commit Strategy

## Purpose

AIが大量のコードを生成した場合でも、
人間が変更内容を追跡・レビューしやすいコミット粒度を維持する。

## Principle

**1 Commit = 1 Logical Change**

1つのコミットには、原則として1つの論理的な変更だけを含める。

## Rules

### 1. 変更の目的ごとにコミットを分ける

以下のように、変更の目的が異なる場合はコミットを分割する。

- 機能追加
- バグ修正
- リファクタリング
- テスト追加
- ドキュメント変更
- 生成ファイルの更新
- 設定変更

### 2. 関係のない変更を同じコミットに含めない

ある機能を実装するために必要な変更は同じコミットに含めてよい。

一方で、その機能とは無関係なリファクタリングやフォーマット変更などは別コミットにする。

### 3. コミットを過度に細分化しない

コミット数を増やすこと自体を目的にしない。

以下のような関連する変更は、同一コミットにまとめてよい。

- 1つの機能を成立させるために必要な複数ファイルの変更
- 実装と、それに直接対応するテスト
- 型定義と、それに伴う必須の実装変更

### 4. コミット単位で変更意図を説明できるようにする

各コミットについて、

> 「このコミットでは何を変更したのか？」

を短い文章で説明できる状態を目指す。

### 5. 大規模な変更はコミット計画を作成してから実装する

変更範囲が大きい場合は、実装前に論理的な変更単位を整理する。

例：

```text
1. API仕様を追加
2. Domain層を実装
3. Service層を実装
4. Repository層を実装
5. Authenticationを実装
6. Handlerを実装
7. テストを追加
8. 生成ファイルを更新
```

### 6. レビュー容易性を優先する

コミットを分割する際は、単純なコード量ではなく、

- 変更意図が明確か
- 差分を追跡しやすいか
- レビュー単位として理解しやすいか
- 他の変更と独立して確認できるか

を基準とする。
